# Логика сервиса учета КТК

Документ описывает текущую бизнес-логику проекта: заявки, события TOS, хранение, оказанные услуги и расчет начислений. Его можно использовать как постоянную шпаргалку при доработках.

## Главная цепочка

```text
Заявки / TOS / SYSTEM
        ↓
service_execution — факт оказанной услуги
        ↓
billing_period — расчетный период по клиенту
        ↓
billing_accrual — сводное начисление за период
        ↓
billing_accrual_source — детализация начисления до оказанных услуг
```

Важно: `service_execution` — это факт оказания услуги, а не деньги. Деньги появляются только в `billing_accrual`.

## Справочники

Основные справочники:

- `operation` — операции.
- `service` — реальные услуги, которые могут оказываться и начисляться.
- `service_operation` — связь услуг с операциями.
- `complex_service` — комплексная услуга для заявки на поставку.
- `complex_service_item` — состав комплексной услуги.
- `tariff` — тариф.
- `tariff_service` — связь тарифа с услугами.

Технические услуги `Смена владельца` и `Хранение КТК` больше не должны использоваться как услуги справочника.

Текущая логика:

- смена владельца — это тип заявки/событие, а не услуга;
- хранение создается и начисляется как реальная услуга `Учет и хранения`.

## Заявки на поставку

При создании заявки на поставку выбирается комплексная услуга.

Комплексная услуга может включать:

- `Учет и хранения`;
- разовые услуги, например `Прием КТК`, `Крановая операция`;
- коэффициент комплексной услуги.

После фактической поставки КТК:

1. создается история владельца с типом операции `RECEIVING`;
2. открывается период хранения `container_storage_period`;
3. источником периода хранения становится заявка/строка поставки;
4. хранение до смены владельца относится на клиента из заявки на поставку;
5. при расчете периода для услуг из комплексной услуги применяется коэффициент.

## Заявки на вывоз

Заявка на вывоз завершает владение/обработку КТК в системе.

При выполнении:

- проверяется текущий владелец;
- создается событие истории владельца с типом `SHIPPING`;
- период хранения закрывается.

## Заявки на услугу

Раздел `Заявки на услугу` поддерживает разные типы заявки.

### Тип `OWNER_CHANGE`

Это заявка на смену владельца.

Она:

- остается в разделе `Заявки на услугу`;
- не является услугой из справочника `service`;
- не создает `service_execution`;
- не попадает в начисления как отдельная услуга;
- работает как триггер смены владельца и хранения.

При выполнении смены владельца:

1. старый активный владелец закрывается;
2. старый период хранения закрывается на дату начала нового владения;
3. начисления хранения на дату смены и позже откатываются/пересоздаются;
4. создается новый владелец;
5. открывается новый период хранения на нового клиента;
6. дальнейшее хранение начисляется новому клиенту.

В карточке КТК:

- `Дата события` для смены владельца — дата создания события/заявки;
- `Дата начала` — дата, с которой новый владелец начинает действовать.

### Тип `SERVICE`

Это заявка на оказание обычной услуги.

Она:

- выбирает реальную услугу из справочника `service`;
- при выполнении создает `service_execution`;
- попадает в будущий расчетный период;
- не меняет владельца КТК.

Для такой заявки `service_execution` создается со следующей логикой:

- `source_type = MANUAL`;
- `basis_type = SERVICE_REQUEST`;
- `basis_id = id заявки`;
- клиент берется как текущий владелец КТК;
- дата оказания услуги берется из даты заявки;
- статус создается `CONFIRMED`.

## Журнал TOS

`tos_operation_fact` хранит входящие факты TOS.

TOS-событие может создать оказанную услугу, если:

1. есть операция TOS;
2. операция найдена в `operation`;
3. операция связана с услугой через `service_operation`;
4. услуга является реальной услугой справочника.

Для TOS:

- `execution_type = ONE_TIME`;
- `source_type = TOS`;
- `basis_type = TOS_OPERATION_FACT`;
- `status = CONFIRMED`;
- количество берется из TOS или равно `1`.

Если TOS-событие связано с заявкой на поставку и услуга входит в комплексную услугу, при расчете применяется коэффициент комплексной услуги.

## Хранение КТК

Хранение состоит из двух уровней:

1. `container_storage_period` — период хранения КТК у клиента.
2. `container_storage_daily_accrual` — ежедневный факт хранения.

При начислении дня хранения:

```text
container_storage_period
        ↓
container_storage_daily_accrual
        ↓
service_execution по услуге "Учет и хранения"
```

Для хранения:

- `execution_type = CONTINUOUS`;
- `source_type = SYSTEM`;
- `basis_type = STORAGE_DAILY_ACCRUAL`;
- `quantity = 1`;
- `unit = сутки`;
- `status = CONFIRMED`.

Повторный запуск начисления за ту же дату не должен создавать дубли.

## Реестр оказанных услуг

`service_execution` — единый реестр фактически оказанных услуг.

В него попадают:

- разовые услуги из TOS;
- услуги из заявок типа `SERVICE`;
- ежедневное хранение из `container_storage_daily_accrual`.

В него не должна попадать смена владельца.

Статусы:

- `DRAFT` — черновик;
- `IN_PROGRESS` — в процессе;
- `CONFIRMED` — оказана и готова к расчету;
- `CANCELLED` — отменена;
- `ERROR` — ошибка формирования.

Статусов `billed`, `accrued`, `invoiced`, `paid` здесь быть не должно.

## Расчетные периоды

`billing_period` — расчетный период по конкретному клиенту.

При создании периода пользователь выбирает:

- клиента;
- дату начала;
- дату окончания;
- название периода.

Расчет периода:

1. период должен быть `DRAFT`;
2. период не должен быть `CLOSED` или `CANCELLED`;
3. берутся только `service_execution`:
   - `status = CONFIRMED`;
   - клиент равен клиенту периода;
   - `date_from` входит в период;
   - услуга еще не включена в начисление этого периода;
4. для каждой оказанной услуги ищется тариф через `tariff_service`;
5. если тарифа нет, расчет прерывается;
6. считается сумма по каждой оказанной услуге;
7. создается одна сводная запись `billing_accrual`;
8. через `billing_accrual_source` она связывается со всеми оказанными услугами;
9. период становится `CALCULATED`.

## Реестр начислений

`billing_accrual` сейчас является сводной записью по клиенту и периоду.

В реестре начислений отображается:

- период;
- клиент;
- количество услуг;
- сумма;
- статус.

Внутри карточки начисления показывается детализация:

- дата/период оказания;
- КТК;
- услуга;
- количество;
- единица;
- источник;
- статус.

## Коэффициенты

Коэффициент комплексной услуги применяется:

- к хранению, если период хранения был открыт из заявки на поставку;
- к разовым услугам TOS, если услуга входит в комплексную услугу заявки на поставку.

После смены владельца хранение идет по обычной услуге `Учет и хранения` без коэффициента старой заявки на поставку.

## Что еще не реализовано

На текущем этапе система не делает:

- счета;
- акты;
- оплату;
- интеграцию с 1С;
- НДС;
- закрытие месяца с жесткой блокировкой;
- перерасчет задним числом;
- сложные правила тарифов;
- скидки и бесплатные дни;
- прогрессивные тарифы.

## Главные правила для будущих доработок

1. Не превращать смену владельца в услугу.
2. Не добавлять денежные статусы в `service_execution`.
3. Все деньги должны жить в `billing_accrual`.
4. Все факты оказанных услуг должны жить в `service_execution`.
5. Все связи начислений с деталями должны идти через `billing_accrual_source`.
6. Хранение после смены владельца должно относиться новому клиенту.
7. Справочник `service` должен содержать только реальные услуги.
